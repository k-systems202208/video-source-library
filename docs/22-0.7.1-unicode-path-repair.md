# 0.7.1 Unicode / 文字化けパス修復

## 背景

0.7.0 の実機診断で、4,869動画のうち `MISSING 41 / NEW_FILE 41` は実際の欠落・追加ではなく、監査済みメタデータ側のローマ字ダイアクリティカル文字が `?` に置換されていたことが原因と判明した。

例:

```text
F?ten      -> Fūten
B?ky?      -> Bōkyō
Torajir?   -> Torajirō
junj?      -> junjō
kamif?sen  -> kamifūsen
```

Windows の実ファイル名には `?` を使用できないため、このケースに限り安全な補正が可能である。

## 方針

通常の完全一致を変更しない。

Windowsランチャーの起動スキャン直前に、SQLite `video_files.relative_path` に `?` を含む行だけを対象に補正候補を確認する。

1. パス区切りを `/` へ統一
2. Unicode NFKD 正規化
3. 結合文字を除去
4. 大文字・小文字を無視
5. メタデータ側 `?` を「ちょうど1文字」のワイルドカードとして比較
6. その他の文字とパス区切りは完全一致を要求

## 一意性

自動補正するのは次の両方を満たす場合だけ。

- 1つのメタデータ行から候補となる実ファイルが1件だけ
- その実ファイルを候補とするメタデータ行も1件だけ

候補が複数ある場合は補正しない。従来どおり `MISSING / NEW_FILE` として診断画面に残す。

## 更新対象

一意に一致した場合、SQLite の次の値だけを実ファイル表記へ修正する。

- `video_files.relative_path`
- `video_files.filename`
- `video_files.extension`
- `video_files.updated_at`

`source_subfolder` は作品内の論理グループ情報なので変更しない。

元動画・字幕ファイルは移動・改名・削除・書換えを行わない。

## 字幕

パス修復は通常スキャンより前に完了する。そのため、その後の字幕照合は `Torajirō` 等の実在する正しい動画パスを使用する。

## 実行コスト

`?` を含むメタデータ行が1件もなければ追加のファイル走査は実行しない。

対象行が存在する場合だけ動画ルートのファイル名を確認する。ffprobe はこの補正処理では実行せず、通常スキャン側の既存キャッシュ判定に従う。

## 期待する実機結果

0.7.0で確認した41件がすべて一意に一致する場合、次回の起動スキャンでは次を期待する。

```text
MATCHED 4869
MISSING 0
NEW_FILE 0
```

字幕 `1234 / 354 / 880` の問題は動画パス修復後に別途診断する。

## 回帰テスト

- `F?ten / Torajir?` と `Fūten / Torajirō` が一意なら修復される
- 修復後のDBに実ファイル名が保存される
- `source_subfolder` は変更されない
- 修復後のパスで動画を解決できる
- 修復後のパスを使って字幕が紐付く
- 1つの `?` に複数の実ファイルが候補になる場合は自動修復しない
- 元ファイルを変更しない
